# 3단계 안정화 · 제한 운영 안내

## 상담과 첫 수업의 기준

- 고객이 신청한 희망 요일·회차는 상담 대안이다. 실제 수업 날짜를 자동으로 만들지 않는다.
- 제안 중인 첫 수업은 시간이 확보되거나 예약된 상태가 아니다. 담당 강사가 고객과 실제 날짜를 합의한 뒤 확정한다.
- 확정 전에 해당 날짜의 **풀장 운영 여부**를 확인한다. 근거는 `예약 페이지에서 날짜·회차 확인`, `풀장 담당자와 통화`처럼 짧게 적는다. 이 기록은 풀장 예약 완료나 결제 완료를 뜻하지 않는다.
- 강사의 반복 가능 시간표 밖에서 합의했다면 고객과 예외 합의한 사실과 사유를 기록한다. 공휴일에는 평일·주말 운영을 추정하지 말고 해당 날짜의 운영 여부를 확인한다.
- 같은 날 다른 풀장의 수업이 있다면 이동 가능 여부를 확인하고 짧은 근거를 남긴다. 판단이 어렵다면 대표에게 확인을 요청한다. 임의의 이동 시간 기준은 적용하지 않는다.
- 이번 화면은 신청당 활성 첫 수업 일정 하나를 관리한다. 기존 일정을 바꿀 때는 새 일정을 추가하지 말고 **일정 변경·취소**를 사용한다. 취소된 일정과 변경 이력은 삭제되지 않는다.
- 상담 종료는 교육 완료가 아니다. 미래 확정 수업이 있으면 먼저 일정을 확인해야 종료할 수 있다. 지난 확정 수업은 다가오는 수업 건수에서 빠지지만, 상담이 열려 있는 동안 확인 필요 목록에 남는다. 실제 진행 여부를 확인한 뒤 상태를 정리한다.

## 대표 휴대폰 점검표

1. 강사 계정으로 로그인해 오래된 신청도 포함한 **전체** 목록에서 배정 신청을 찾는다.
2. 신청 상세에서 고객의 원래 희망 일정과 상담 상태가 구분되는지 확인한다.
3. 실제로 수행한 연락 결과와 다음 할 일만 기록하고 저장한다. 저장 후 상세를 닫았다가 다시 열어 값이 유지되는지 확인한다.
4. 메모 입력 중 휴대폰 키보드가 입력칸과 저장 버튼을 가리지 않는지 확인한다.
5. 상태를 바꿔 저장한 뒤 홈 건수와 상세 상태가 맞는지 확인한다. 오류가 뜨면 입력 내용이 남아 있는지 확인한다.
6. **수업 취소**는 신청 삭제나 상담 종료가 아닌지, 저장 버튼과 취소 상태의 뜻이 분명한지 확인한다.
7. 실제 운영 신청으로 점검한다면 사실에 맞는 기록만 입력한다. 고객과 합의하지 않은 수업을 테스트 목적으로 확정하거나 취소하지 않는다.

제안·확정·변경·취소 전체 시나리오는 격리된 PostgreSQL 테스트에서 확인한다. 현재 `/TEST`는 홈페이지 테스트 경로이며 상담·수업용 별도 DB와 테스트 강사 계정이 확인되지 않았다. 운영 DB를 쓰는 미리보기에서 가짜 신청을 생성하지 않는다.

## 대표·강사 2~3명 제한 운영

1. **새 신청 확인:** 강사 페이지에 로그인해 배정 신청 목록을 직접 확인한다. 자동 알림은 없으므로 초기 사용 기간에는 사람이 정기적으로 확인한다.
2. **연락 후 기록:** 전화 버튼을 눌렀다는 사실만으로 연락 완료로 기록되지 않는다. 실제 연락 결과를 짧게 입력하고 상태를 변경한다. 내부 메모에는 불필요한 민감정보를 적지 않는다.
3. **다음 할 일:** 담당 강사가 할 일과 예정 시각을 입력한다. 완료 체크 후 내용·날짜를 바꾸면 새 할 일로 취급해 완료 상태가 해제된다.
4. **첫 수업:** 날짜·풀장·시간을 제안한다. 고객 합의와 그 날짜의 풀장 운영을 확인한 뒤 확정한다. 풀장 예약·결제 여부는 별도로 확인한다.
5. **변경·취소:** 기존 일정에서 변경한다. 확정 일정을 바꾸면 고객 합의와 풀장 운영을 다시 확인하고 변경 사유를 적는다. 취소 후에도 신청과 상담 기록은 남는다.
6. **문제 보고:** 대표에게 신청 ID, 화면, 발생 시각, 하려던 행동, 보이는 오류 문구를 전달한다. 고객 이름·전화번호를 단체 채팅이나 공개 오류 캡처에 불필요하게 공유하지 않는다. 저장 실패 시 반복 클릭 전에 상세를 다시 열어 저장 여부를 확인한다.

## 공유 관리자 계정의 이력 한계

현재 관리자 로그인은 공유 계정이므로 변경 이력의 `관리자`는 **어느 개인이 변경했는지 증명하지 못한다**. 대표 한 명만 관리자 계정을 사용한다면 대표가 이력을 확인하는 방식으로 제한 운영할 수 있다. 여러 명이 관리자 작업을 해야 한다면 개인별 관리자 계정과 권한, 세션, 감사 기록 전환을 후속 작업으로 진행한다. 자유 입력한 이름을 본인 확인된 감사 기록으로 취급하지 않는다. 이번 단계에서 새 관리자 계정이나 권한은 만들지 않는다.

## 배포 복구 절차와 제한

- 현재 배포에서 화면 문제가 생기면 배포 상태와 DB 연결 상태를 먼저 확인한다. 데이터베이스 마이그레이션은 추가형이며 수업·상담 기록은 애플리케이션 배포를 되돌려도 남는다.
- 3단계 안정화 이전 화면으로 되돌리는 것만으로 DB의 **확정 수업 시간 겹침 차단**, **신청당 활성 첫 수업 하나**, **미래 확정 수업이 남은 상담 종료 차단**이 사라지지 않는다. 이들은 DB 제약과 트리거다.
- 3단계 직전 배포 `4c72564`까지 되돌리면 새 상담·수업 화면과 API가 없어 기록을 조회·변경하기 어렵다. **수업 제안·확정·변경·취소 업무는 중단**하고 대표가 기존 확정 수업을 별도로 확인한 뒤 정상 버전을 다시 배포한다. 기록이 DB에 남는 것과 업무를 정상 수행할 수 있는 것은 다르다.
- 같은 3단계의 안정화 이전 배포로 돌아가면 신규 화면은 있으나 이전의 중복·상태 처리 결함이 재발할 수 있다. 복구 중 상담·첫 수업 변경은 중단한다.
- `4c72564`는 2단계 요일별 매칭을 유지한다. 그보다 이전 버전은 새 요일별 시간표를 매칭에 정확히 반영하지 않을 수 있으므로 신규 매칭 계속 허용 여부를 대표가 판단해야 한다.
- 고객 배정, 기존 신청, 강사 프로필, 수업 기록을 되돌리거나 삭제하는 DB 롤백은 자동으로 수행하지 않는다. 화면 복구 후 기록을 대조해 업무를 재개한다.
