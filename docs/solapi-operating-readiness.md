# 신규 상담 운영 전환 기록

## 현재 확인

- 운영 `main`의 메인 화면, 코스 카탈로그와 기존 `/api/matches`는 수정하지 않았다. 새로운 상담은 `/api/consultations`에서만 강사 미배정으로 저장한다.
- 운영 Supabase에 `20261108054503_direct_consultations` 마이그레이션이 적용됐다. 적용 전 전체 DB 논리 백업은 비공개 작업 공간에 보관하고 SHA-256을 대조했다. 격리 PostgreSQL에서 공개 스키마 9개 테이블 복원과 강사 10건·신청 0건 일치를 확인했다. 현재 Auth 사용자는 0건, Storage 파일은 0건이다.
- Supabase Free 요금제에는 자동 일일 백업이 없다. 적용 전 덤프는 `/workspace/.bluepeace-backups/bluepeace-pre-direct-20261108.dump`(소유자 전용 권한 600, 2,077,340바이트, SHA-256 `e6fd5959890de12a85b5984cf483f3865b94f4d743df36c739ba176ccd3173f5`)에 보관했다. 외부 공개 장소에 복사하지 않았다. 완전한 Supabase 관리형 환경 복원 대신 격리 PostgreSQL에서 실제 앱 공개 스키마·데이터 복원을 검증했다.
- 2026-11-08 확인: 운영 Vercel의 등록된 SOLAPI 키와 번호로 대표에게 실제 테스트 문자 1건이 SOLAPI에 접수되고 수신까지 확인됐다. 점검용 도메인 미연결 배포와 임시 토큰은 삭제했다. Production에 `SOLAPI_ENABLED=true`와 `BLUEPEACE_DIRECT_PRIVACY_VERSION=2026-11-08-v1`을 등록했다. 기존 운영 도메인은 아직 이전 배포를 가리킨다.
- 공개 데모에는 `BLUEPEACE_PUBLIC_DEMO=true`, `NEXT_PUBLIC_NAVER_WCS_ENABLED=false`, 모의 Supabase URL/키가 설정되어 있다.
- `customer_direct_alerts`는 새 직접 상담 삽입과 같은 DB 트랜잭션에서 1건 생성한다. `pending -> sending` 원자적 claim을 통과한 요청만 업체에 전달한다. SOLAPI가 응답에 접수 성공을 명시한 경우에만 `sent`(업체 접수)로 기록하며, 단말기 수신 성공으로 해석하지 않는다.
- 명확한 접수 실패는 `failed`, 미설정은 `skipped`, 응답 손실이나 서버 오류 등 결과 불명은 `unknown`으로 기록한다. `unknown`과 오래된 `sending`은 자동 재발송하지 않고 SOLAPI 발송 내역에서 먼저 대조한다. 관리자 재시도는 `pending`, `skipped`, `failed`에서만 허용된다. `failed` 재시도 전에는 업체 접수 여부 확인을 요구한다.

## SOLAPI 계정 준비

1. 운영자가 SOLAPI에 가입하고 본인 실명 인증을 완료한다. 개인 계정으로도 문자 이용이 가능하므로 사업자 인증은 무조건 필수는 아니다. 사업자 계정과 명의/세금계산서가 필요하면 사업자 인증을 진행한다.
2. 대표 본인 명의의 휴대전화 발신번호는 SOLAPI 콘솔에서 ARS 추가 인증 후 문자 본인인증 또는 통신서비스 이용증명원으로 등록한다. 사업자 명의 전화나 다른 사람 명의 번호는 별도 서류가 필요하다.
3. SOLAPI 콘솔에서 API Key와 API Secret을 발급하고 문자 발송 권한을 확인한다.
4. 최초 실명 인증 후 지급되는 300P가 남아 있다면 테스트 LMS에 사용할 수 있다. 잔액이 부족하면 충전이 필요하다. 카드 충전 공식 최소액은 1,000원이며 테스트 발송도 실제 요금 또는 포인트를 차감한다. 실제 계정의 단가와 잔액은 운영자가 콘솔에서 확인한다.
5. 운영 Vercel 프로젝트의 **Production 전용 서버 환경변수**에 `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `SOLAPI_SENDER_PHONE`, `SOLAPI_ADMIN_PHONE`을 민감값으로 입력한다. 번호는 발신 등록번호와 대표 수신번호를 각각 넣는다. 키·번호를 채팅이나 Git에 올리지 않는다. 모두 확인하고 실제 발송 테스트가 승인된 뒤 `SOLAPI_ENABLED=true`를 설정한다. Preview와 공개 데모에는 실제 값과 활성화 값을 넣지 않는다.

등록된 운영 키와 번호로 고객 정보 없는 문자 1건을 발송했고 대표가 휴대전화 수신을 확인했다. 운영 DB에 테스트 신청을 만들지 않았다.

2. 남음: 개인정보 처리 관계 확인 후 운영 도메인 미연결 Production 배포에서 새 상담 화면·관리자 API·동의 버전을 검증한다. 기존 메인과 코스 카탈로그는 코드에서 변경하지 않았다.
3. 남음: 검증된 배포를 운영 도메인으로 연결한다. `SOLAPI_ENABLED=true`는 이미 Production에 등록됐다.
4. 배포 직후 운영자의 합의된 **실제 상담 1건**으로 저장, 관리자 조회, 대표 LMS 수신, 상태 기록, 네이버 전환 1회, 수동 배정, 기존 매칭 화면을 확인한다. 테스트용 가짜 고객 신청은 운영 DB에 만들지 않는다.

## 승인 후 문자 1건 점검 절차

- 운영 DB에 가짜 상담을 만들지 않는다. 승인 후 서버에서 기존 SOLAPI 인증 함수를 사용해 대표 수신번호로 `[블루피스 문자 연동 점검]` 1건만 직접 보낸다. 본문에는 실제 고객 정보나 신청 완료 문구를 넣지 않는다.
- 발신번호는 등록된 발신번호, 수신번호는 Production `SOLAPI_ADMIN_PHONE`만 사용한다. 사전에 번호 형식·변수 존재·공개 데모 아님을 확인하고, 발송 요청은 1회만 수행한다. 성공·실패·결과 불명 중 하나로 기록하되 키와 번호 전체는 출력하지 않는다.
- `SOLAPI` 접수 성공은 휴대전화 수신 성공과 다르다. 대표가 1건 수신을 확인한 후에만 `SOLAPI_ENABLED=true`를 Production에 설정한다. 응답이 불명확하면 업체 발송 내역을 대조하기 전 재발송하지 않는다.

## 문제가 생겼을 때

- SMS만 실패하면 `SOLAPI_ENABLED=false`로 신규 문자 발송을 중지한다. 상담 저장은 계속되고 관리자 화면의 알림 상태로 누락 건을 찾는다. 실패 또는 결과 불명 건을 무조건 재전송하지 않는다.
- 상담 저장이나 관리자 기능이 실패하면 신규 상담 접수를 잠시 제한하고 운영 배포를 이전 안정 버전으로 되돌릴지 판단한다. 이전 코드가 새 직접 상담 상태를 이해하지 못하므로, 코드 롤백만으로 정상 운영 복구가 완료되지는 않는다.
- 이미 저장된 직접 상담·알림 기록을 보존하기 위해 기본 복구에서 새 컬럼과 테이블을 삭제하지 않는다. DB 자체를 복원해야 한다면 백업 시각 이후 신청 유실 가능성을 먼저 산정하고 운영자가 결정한다.
