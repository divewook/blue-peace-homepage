# 2차 개편 운영 배포 전 점검 (2026-11-04)

## 환경 경계

- 운영: `www.bluepeace.co.kr`, 기존 `blue-peace-homepage` Vercel 프로젝트와 Supabase `swaythksaerdxcdpmrdq`. 이 작업 중 배포·DDL·테스트 행 삽입을 하지 않는다.
- 공개 검수: `https://bluepeace-public-demo.vercel.app/TEST`의 별도 Vercel 프로젝트. Supabase 주소·키는 자리표시자, API와 관리자·강사 경로는 404, 상담 제출은 모의 완료다. `/TEST/review`의 이미지는 로컬 브라우저에서 자동 캡처하며 관리자 이미지는 가상 데이터다.
- 격리 DB: `scripts/test-direct-consultation-db.sh`가 네트워크 없는 일회용 PostgreSQL 17 컨테이너를 만들어 관련 migration과 가상 기록 검증 후 제거한다. 운영 DB와 연결하지 않는다.
- 격리 API: 별도 로컬 PostgreSQL 17 + PostgREST 12.2 + Next 개발 서버에 가상 강사·고객만 만들었다. 서버 API를 통해 신규 접수 `201`, 같은 요청 재시도 `200`, 관리자 로그인·목록·상태·메모·배정 `200`, 담당 강사 조회 `200`, 다른 강사 접근 `403`, 과거 자동 매칭 행 조회, 구형 행의 직접 상담 변경 거절 `409`, DB 연결 실패 시 `503`과 입력 유지까지 확인했다. 테스트 종료 후 컨테이너·네트워크를 제거했다.
- 격리 광고: 실제 네이버 연결을 쓰지 않고 가짜 `wcslog.js` 응답으로 신규 저장 시 `lead` 1건, 완료 화면 새로고침 시 추가 0건을 확인했다. 스크립트 차단 시에도 상담 저장은 완료됐다.
- 운영 Supabase는 메타데이터만 읽었다. `customers`에 기존 `request_key`, `request_status`가 있고, `customer_workflows`가 있다. 새 `consultation_source` 컬럼과 새 RPC는 없다. 조회 시 고객 행은 0건이었다. 이 숫자는 배포 시 다시 확인한다.
- Supabase 개발 브랜치는 현재 프로젝트의 요금제에서 지원하지 않아 생성하지 못했다. 로컬 PostgREST 검증은 운영 Supabase 프로젝트의 실제 설정까지 검증한 것은 아니다.

## 구현된 저장 흐름

1. `/api/consultations`는 필수 이름·전화·동의와 UUID를 서버에서 검사한다. `request_key` 고유 인덱스로 중복 저장을 막는다. 신규 행에는 `consultation_source='direct'`, `consultation_status='new'`, `request_status='pending_assignment'`, 강사 ID `null`을 기록한다.
2. 관리자는 기존 로그인 쿠키를 거쳐 `/api/admin/data`로 신청을 조회한다. `save_customer_workflow`로 배정 전에도 내부 메모·연락 결과·다음 할 일을 기록한다.
3. 관리자 배정 API는 인증·승인·교육 가능 범위를 먼저 확인하고 새 DB RPC에서 수정 버전·승인 여부·중복 요청을 다시 확인한다. 기존 `matched_instructor_id`와 배정 이력 트리거를 사용한다. 담당 강사가 바뀌면 이전 강사는 `/api/instructor/customers`에서 현재 신청을 조회할 수 없다.
4. 프런트엔드는 서버가 신규 저장에 `201`로 응답할 때에만 네이버 `lead` 이벤트를 시도한다. 중복 응답 `200`, 모의 제출, 미동의, 광고 스크립트 실패는 전환을 보내지 않는다. 전환 코드·기존 광고 키는 변경하지 않는다.
5. 기존 자동 매칭 요청과 강사 일정 데이터는 보존한다. 고객의 새 진입 경로만 대표 직접 상담으로 바뀐다.

## 운영 반영 순서와 복구

1. 운영자의 명시적인 배포 승인과 개인정보처리방침 확정 후, 현재 Vercel 환경 변수·Supabase 스키마·백업 상태를 다시 확인한다.
   최종 시행 버전을 서버 전용 `BLUEPEACE_DIRECT_PRIVACY_VERSION`에 설정한다. 미설정 시 신규 직접 상담 API는 접수를 거절한다.
2. 기존 DB 백업 및 복구 지점을 확인한다. `supabase/migrations/20261104040000_direct_consultations.sql`을 운영 적용하기 전 격리 환경에서 실제 Supabase Data API와의 통합 검증을 마친다. 새 컬럼·이벤트 테이블·RPC는 기존 행을 재해석하거나 삭제하지 않는다.
3. DB migration 적용 후 새 코드의 서버 API 및 관리자 권한·강사 접근 검사를 확인하고 운영 프로젝트로 배포한다. 새 상담 경로와 광고 전환 1건 검증은 실제 고객 데이터 없이 허용되는 별도 테스트 구성에서 해야 한다.
4. 장애 시 새 코드 배포를 이전 정상 버전으로 되돌리고 새 상담 접수를 잠시 제한할지 운영 판단한다. DB 변경을 즉시 역방향으로 삭제하지 않는다. 새 상담 행이 존재하면 이전 화면에서 보이지 않거나 기존 자동 매칭 흐름과 의미가 달라질 수 있다. **데이터 보존**과 **구버전에서 정상 운영**은 별개다.
5. 데이터 스키마 복구가 꼭 필요한 경우 새 필드·이벤트를 먼저 내보내고 의존 코드·RPC·정책을 확인한 뒤 별도 계획으로 진행한다. 단순 `DROP COLUMN` 롤백은 신규 상담 기록을 잃으므로 금지한다.

현재 기술 판단: 운영 배포 전 **실제 Supabase Data API 통합 검증과 개인정보 운영 정책 확정이 남아 있다**. 공개 미리보기는 운영 배포 승인이나 실제 신청 검증을 대신하지 않는다.
